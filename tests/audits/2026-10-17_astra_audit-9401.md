## Incidents de code restants

### P1 — Écran, fiche et Excel ne calculent pas les mêmes heures

Lignes 7391, 7799, 8396 ; `monthHoursUsed`, 3431–3449.

L'écran appelle `monthHoursUsed(a,cells,mDs,outsideRes)`. La fiche et Excel omettent `outsideRes`.

Reproduction : contrat 37,5 h ; congés connus du 26 au 30 octobre ; OFF le 31 ; congé le 1er novembre. Avec le contexte octobre, la semaine a déjà ses cinq crédits : contribution du 1er novembre **0 h**. Sans ce contexte, elle devient **7,5 h**. Le même planning peut donc afficher deux totaux selon le support. Claude signale Excel dans sa note, mais **la fiche est concernée aussi**.

Correction simple : calculer une fois les compteurs avec le contexte du plan, et fournir ce résultat à tous les consommateurs.

```js
// Dans le résultat du calcul, avec le même outside que finalCheck :
const hoursByAgent = Object.fromEntries(agents.map(a => [
  a.id, monthHoursUsed(a, cells, dates, outside)
]));
// Écran, fiche, Excel : hoursByAgent[a.id] / 60.
```

Associer le résultat au magasin et au mois ; recalculer quand les cellules, le contrat ou les jours voisins changent. Ne pas dupliquer un nouveau resolver dans chaque export. Les jours inconnus doivent rester signalés comme tels ; ne pas les transformer silencieusement en repos certains.

### P1 — Un OFF explicite devient crédit d'absence un jour férié fermé

`accountDay`, 3422–3426 :

```js
var leave = (res && res.special === 'leave') || getDayClosureType(ds) === 'holiday';
```

Reproduction : temps plein 37,5 h, jeudi 5 novembre déclaré férié fermé, cellule `{code:'OFF',special:'off'}`. Retour **{work:0,credit:450}**. La note et le commentaire annoncent pourtant OFF=0. Le test de Claude ne le voit pas car il utilise un part-time dont ce jeudi n'est pas un jour fixe : `absenceCredit` renvoie déjà zéro.

Correction ciblée à placer avant le traitement férié :

```js
if (res && (res.code === 'OFF' || res.special === 'off'))
  return { work: 0, credit: 0 };
```

Conserver le traitement distinct d'une fermeture réellement subie sur un jour de travail. Ajouter le test temps plein, pas seulement le part-time fixe. Les absences sur dates de travail inconnues restent un sujet de qualité de données ; H/5 demeure une convention, pas une déduction du planning individuel.

### P2 — `special:'closed'` contourne le nouveau contrôle des données

`finalCheck`, 7524 :

```js
if (r.special === 'closed') return;
```

Reproduction sur plan synthétique, voisins connus : une cellule du 2 novembre, journée ouverte, devient `{code:'NONEXISTENT',special:'closed'}`. Résultat **checked**, aucune erreur `data|`. Les autres personnes assurent la couverture : le défaut reste invisible.

Correction : vérifier d'abord la cohérence cellule/journée. N'accepter le marqueur closed que sur une vraie fermeture et avec la représentation de fermeture attendue. Contrôler aussi la compatibilité des autres marqueurs : O ne doit pas devenir non-travaillé simplement parce qu'un objet porte `special:'leave'`. Une petite fonction `validateCell` suffit ; pas une nouvelle passe de réparation.

Ce test porte sur une donnée incohérente sauvegardée/importée, pas sur une saisie courante reproduite dans l'UI.

## Architecture et simplification pour Claude

1. **Un résultat de calcul unique pour les compteurs.** `accountDay` est un progrès, mais la centralisation d'une fonction ne suffit pas si ses appels reçoivent des contextes différents. Inclure heures par agent, diagnostic et contexte de période dans le résultat de calcul.
2. **Normaliser et valider avant d'optimiser.** `{code,special,half,corner}` ne doit pas permettre des états contradictoires. Le validateur doit contrôler ces relations avant les règles de couverture/repos.
3. **Conserver des modifications testées**, ne pas empiler trois correcteurs de compteur. Le moteur de placement n'a pas besoin de changer pour les deux erreurs d'affichage/comptage ci-dessus.
4. **Tests : comparer les violations, pas seulement leur nombre.** `regression-9401.cjs` permettrait une infraction nouvelle si une ancienne disparaissait, car il compare des longueurs. Pour les cas déjà tous à zéro cela passe correctement ; pour les prochains cas dégradés, comparer clés et amplitudes ou utiliser `mandatoryAdded`.
5. **SQL : qualifier le CHECK par table.** Le test d'existence devrait ajouter `conrelid = 'public.retail_agents'::regclass` au nom. Inspection seulement ; pas d'échec reproduit en base.
6. **Colonnes RH : centralisation partielle.** `RH_COLUMNS` règle le nombre, mais en-têtes, valeurs et largeurs Excel restent codés séparément. À terme une liste de descripteurs évitera la prochaine divergence. Pas besoin de refonte CSS.
7. **Noms et commentaires :** `monthCapMin` est maintenant une référence, donc `monthReferenceMin` serait plus juste. Le commentaire de `monthHoursUsed` disant que la semaine « never gets more » est trop large : le code plafonne les crédits, pas le travail déjà saisi. Corriger le commentaire, pas masquer des heures réelles.
8. **Dette inchangée, à traiter séparément :** sauvegarde agent/préférences en deux requêtes ; absence de date d'effet des contrats ; statut du snapshot non conservé ; `finalCheck` lit encore des globals. Ne pas appeler cette transition « achevée » ; ne pas bloquer les corrections courtes sur une réécriture globale.
