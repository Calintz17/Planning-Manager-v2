## Incidents de code — une règle existe mais n'est pas appliquée

### C1 — P1 : les horaires fixes échappent au plafond du contrat
Règle : heures strictes pour les affectations automatiques.
Reproduction synthétique locale : prendre un vendeur sans absence, lui attribuer PART_TIME et fixed_schedule enabled avec days=[1,2,3,4,5], start=480, end=1080 ; conserver weekly_hours=37.5 et Lunch=60. Le résultat donne quatre semaines pleines à 2700 minutes (45 h) au lieu de 2250 (37h30).
Code précis :
- retail.html vers 5923 : `if (a && isFixedTimed(a)) { plan[id] = 'PT'; return false; }`
- vers 6107 : `if (isFixedTimed(a)) return;` dans le contrôle hebdomadaire final.
- saveAgentEditor vers 7012–7020 valide les jours et start/end mais pas la durée payée journalière ni hebdomadaire de ce contrat fixe.
Proposition simple : valider les minutes payées du contrat fixe à l'enregistrement avec le même calcul de durée que le moteur ; refuser une configuration incompatible avec les plafonds existants avec une explication dans le formulaire. Ajouter aussi une vérification finale qui détecte un contrat fixe déjà incompatible en base. Ne pas supprimer silencieusement ses jours fixes. Si des contrats différents sont souhaités, cela nécessite un arbitrage explicite, pas un bypass.

### C2 — P2 : OUT compté comme présence floor dans le Dashboard
Règle : OUT est une journée travaillée hors floor.
Code vers 5129 :
`if (r && r.code && r.code !== 'OFF' && r.code !== 'A' && r.code !== '')`
OUT passe cette condition et augmente poolAgents et cornerPresence.
Reproduction locale : une journée avec une cellule OUT affiche cette cellule dans le pool des présents du Dashboard.
Proposition : `if (r && workHoursOf(a, presDs, r))`. Employer cette même définition de présence onsite pour les compteurs et exports ; ne pas réutiliser la définition « travaillé » de runOk qui doit inclure OUT.

### C3 — P3 : aide contraire à la règle Sunday single shift
Code vers 2302 : `Open public holidays always use the single shift D.`
Le moteur rend D conditionnel à Sunday single shift.
Proposition : expliquer que dimanche et férié ouvert utilisent D uniquement si l'option est activée ; sinon catalogue normal.

### C4 — tests partagés : garantie 0/0 non reproduite
Le setup joint garde le code PRF sous forme de chaîne contenant une liste d'identifiants. Le corriger en PRF.
Replay des JS joints, horloge 31 octobre : aucun dépassement des règles de jours/heures/repos, mais un corner sans ouverture et un autre sans fermeture sur le 10 du mois. Résultat identique après correction du code PRF. La différence d'horloge peut modifier octobre puis l'historique transmis à novembre : la date simulée doit être publiée et partagée.
check_rules.js calcule le maximum global de série puis une seule date bestAt. Pour une vérification limitée à la nouvelle période, cela peut masquer une série nouvelle moins longue qu'une ancienne série historique. Tester chaque franchissement de la limite avec ses dates.
Remplacer les constantes 2250, 660, 60, 5 par weekly_hours, rest_gap_hours, durée non payée et max_days issus des réglages. Fixer l'horloge ; lire le code à un SHA précis ; séparer nouveau planning et snapshot ancien.

## Arbitrages — règle à créer ou à préciser

### A1 — magasin ouvert avec trafic nul
Problème : le poids nul réduit le staffing jusqu'aux minima globaux du magasin, sans assurer une présence dans les quatre corners. Les minima de places lors de la rotation ne créent pas les agents nécessaires.
Proposition : sur un jour ouvert, poser un plancher d'effectif indépendant du trafic, calculé d'après les besoins de couverture des corners actifs et les personnes admissibles. Le trafic répartit le surplus. Si le zéro signifie « manque de prévision », le distinguer d'un zéro de demande validé ; ne pas inventer de trafic.
À décider par Roman : quel minimum par corner actif, notamment sur les jours fériés ? Un agent peut parfois couvrir les deux limites selon ses horaires ; ne pas coder universellement « deux agents » sans vérifier la couverture effective.

### A2 — capacité insuffisante après application des heures strictes
D1 est tranché : ne pas augmenter automatiquement les heures.
Problème : certains minima ne sont pas atteints dans le stress. « Un jour retiré n'est pas reporté » limite aussi l'utilisation de la capacité.
Proposition : avant d'abandonner une couverture, chercher un échange de jour avec un agent disponible, restant dans ses heures, jours max, repos et règles fixes. Une passe de remplacement bornée et locale suffit d'abord ; éviter un nouveau solveur complexe.
À décider si aucune solution admissible n'existe : priorité des corners/minima et traitement manuel de la journée. Aucun dépassement silencieux, aucun avertissement orange ajouté sans demande.

### A3 — limite consécutive couplée à max_days
max_days est utilisé pour le plafond hebdomadaire et pour runOk. Ces règles peuvent différer selon le contrat ou la boutique.
Proposition : confirmer que cette égalité est souhaitée pour toutes les boutiques. Si oui, conserver le code simple ; sinon une clé dédiée max_consecutive_days avec repli sur max_days. Ne pas présenter ce réglage comme preuve de conformité juridique.
