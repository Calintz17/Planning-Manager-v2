## A — Incidents de code et corrections précises

### P1 — Le nouveau choix des shifts peut dégrader la viabilité

Reproduction : `setup.js`, C prolongé à 12:00–21:00 (8 h payées), `min_closing=3`, heures strictes 37,5. Exécuter `check_rules.js` sur octobre/novembre/décembre, horloge 31 octobre.

| Contrôle | 9.3.2 | 9.3.3 |
|---|---:|---:|
| Corner-jours totalement vides en novembre | 0 | **2** |
| Corner-jours sans ouverture | 8 | **14** |
| Corner-jours sans fermeture | 18 | 16 |
| Quarts d'heure de corner vide en novembre | 150 | **180** |
| Semaines au-dessus de 37,5 h sur la séquence | 3 | **8** |

Les deux corners totalement vides sont RTW et SHO le 1er novembre. Les dépassements horaires sont des semaines **d'octobre, reconstruit rétrospectivement**, à 38 h : ne pas les présenter comme huit dépassements nouveaux en novembre. En horloge 30 septembre, les heures restent strictes (0 dépassement dans les deux versions), mais le trou de couverture se dégrade encore : corner-jours sans fermeture **16 → 22**, quarts d'heure vides **170 → 200**. La dégradation ne se réduit donc pas à l'effet du passé.

Code : nouveau `best()` et amélioration locale lignes **6291–6370** ; les candidats sont filtrés par `restOk` et la moitié tôt/tard, pas par le budget horaire. `settleWeekHours()` intervient ensuite, lignes **6069–6124**, et peut supprimer une présence. Le garde-fou lignes **6936–6947** compare avec/sans habitudes **à l'intérieur de la 9.3.3** : il ne protège pas de cette régression par rapport à la 9.3.2.

Proposition simple : conserver la version faisable du jour/de la semaine avant optimisation ; n'accepter un changement qu'après contrôle des heures restantes et de la couverture finale. Si nécessaire chercher un échange admissible avant de retirer une journée. Si le candidat aggrave la couverture ou une règle, reprendre le candidat antérieur. Ne pas ajouter une nouvelle passe de correction qui casse une règle déjà réparée. Une solution mathématiquement impossible reste à signaler au manager, sans dépassement automatique ; elle ne justifie pas de faire pire que le plan précédent.

La note de Claude reconnaissait une régression de début de mois ; ce banc la confirme et élargit les mesures. « Scénario impossible » explique les trous préexistants, pas leur aggravation.

### P2 — Les horaires non alignés sur 15 minutes sont mal valorisés

Code **6255** :

```js
var p = slots.map(function(sl) {
  return sl.t >= st && sl.t + 15 <= en ? 1 : 0;
});
```

Le catalogue accepte chaque minute (`hourMinOptionsPair`, **2574–2589**), y compris les shifts japonais à :50. `floorOf` jette les fractions de créneau. Probe sur le vrai corps de la fonction, sans pause, magasin 11:00–21:00 :

- 11:50–20:20 : **510 minutes réelles, 495 minutes valorisées** ;
- 12:00–20:30 : **510 minutes réelles, 510 minutes valorisées**.

Ce biais est précisément pertinent pour la question de Roman sur 9:50. Remplacer l'indicateur par la fraction d'intersection :

```js
Math.max(0, Math.min(en, sl.t + 15) - Math.max(st, sl.t)) / 15
```

Utiliser le même calcul dans la métrique d'adhérence : son test ponctuel actuel (`h >= startH && h < endH`) n'a pas non plus la même convention. Ajuster également la soustraction des pauses aux minutes réellement communes. Un moteur et son banc doivent compter le même temps.

### P2 — Le score historique ne départage pas seulement les égalités

Code **6290–6297** :

```js
var g = gain(s);
var sc = g + habits.shift(a, d.dow, s.code, grid.length) * Math.abs(g);
```

Contrairement au commentaire « Traffic first » et à la note « à valeur égale », cette formule peut préférer un gain inférieur. Illustration analytique : gain 10, habitude −0,3 → score 7 ; gain 9, habitude +0,6 → score 14,4. Ce n'est pas une mesure d'un planning généré, c'est une conséquence directe de la formule.

Si l'intention est bien « trafic d'abord, habitude à égalité », comparer d'abord `g`, puis l'habitude avec une tolérance numérique définie. Si l'on conserve un compromis pondéré, le décrire honnêtement et mesurer sa perte d'adhérence. Dans tous les cas, la viabilité reste bloquante.

### P2 — Une pause manuelle peut disparaître lorsque sa fenêtre automatique est impossible

Déplacement ordinaire : **réussi dans Firefox**. Lunch réglé 12–15 h déplacé à 15:15 ; 915 minutes enregistrées dans le stub, puis déjeuner toujours à 15:15 après rendu. Il n'y a donc pas de blocage systématique de la fenêtre au drag dans ce candidat.

Contre-exemple : shift 12:00–20:30 ; fenêtre Lunch 10–11 ; valeur manuelle `intradayOverrides[id + ':lun'] = 795` (13:15). La valeur reste enregistrée mais aucun déjeuner n'est rendu.

Cause **4212–4217** : `if (!starts.length) return;` intervient avant la lecture des positions manuelles **4222–4227**. Sans candidat automatique, le job n'existe plus, même si son horaire manuel est parfaitement représentable.

Correction : charger les missions/positions manuelles **en premier**, créer leurs jobs indépendamment des fenêtres automatiques, les réserver, puis calculer uniquement les tâches non fixées par le manager. Une seule convention de source `manual`/`auto`, partagée par rendu, sauvegarde, exports et apprentissage.

### P2 — Les retours de confirmation sont trop peu contrastés en sombre

Code CSS **19**, **304–306** : `#toast` garde du texte blanc, alors que `--ok` devient `#5DBB98` et `--dang` `#E0718C`. Contrastes calculés : **2,33:1** et **3,04:1**. Les petits textes usuels visent 4,5:1 selon WCAG 1.4.3. Le bouton primaire blanc sur `--brand:#4A78BC` est à **4,46:1**, juste sous ce seuil.

Correction locale : garder des fonds de confirmation assez foncés et réserver les verts/roses clairs au texte ou aux icônes ; ajuster légèrement le fond primaire. Pas de refonte de palette nécessaire. Référence : https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html

## C — Arbitrages métier réellement ouverts

### 1. Late shifts target peut empêcher l'optimum trafic

Japon B, late 0 %, minima 0/0 : le moteur reste dans la moitié tôt et ne couvre pas la soirée après 19:15. Ce n'est pas réparé en 9.3.3, mais c'est cohérent avec la consigne dure actuelle. Choisir davantage de shifts ne résout pas ce conflit.

**Proposition** : offrir un mode explicite « Automatic from traffic » ; garder le pourcentage imposé pour les boutiques qui le veulent. Ne pas remplacer automatiquement un 0 % existant par 50 %. La classification tôt/tard par moitié du nombre de codes (**6234–6240**) change aussi lorsqu'on ajoute des shifts : on ne peut pas promettre que tout ajout de code améliore nécessairement le résultat sous cette contrainte.

### 2. Coût du sous-effectif contre coût du sureffectif

La fonction actuelle pénalise symétriquement les écarts au carré. C'est une règle possible, pas une vérité économique. Si Roman veut que manquer d'une personne coûte plus qu'en avoir une de trop, il faut fixer cette priorité.

**Proposition** : conserver le score symétrique comme référence tant qu'aucune décision n'est prise ; tester séparément une pénalité de manque ×2, sans dégrader les règles ni changer l'effectif. Cette préférence reste à valider, elle n'est pas un incident de code.

Le temps de préparation avant ouverture n'est pas inclus dans l'objectif trafic. Ce périmètre n'est pas rouvert ici : la préparation avait été laissée aux shifts créés par le manager.

## E — Optimisation et simplicité

1. **Bonne simplification** : retrait du bonus `shiftUse` qui concentrait artificiellement les codes ; cache des profils `floorOf` par horaires ; pas de limitation à trois shifts. Pas besoin de forcer l'utilisation de tous les codes.
2. `renderMonthlyPlanning` reste calcul + validation + rendu + sauvegarde + recalcul récursif. Extraire un calcul pur renvoyant plan/diagnostics, un validateur et un rendu ; réutiliser les mêmes contraintes avant/après les échanges. Le contrôle doit porter sur le candidat final, pas sur un état intermédiaire différent.
3. La nouvelle passe s'arrête après **six tours au maximum** (**6349**), pas nécessairement après convergence. Une recherche locale à une personne, contrainte à sa moitié tôt/tard, n'est pas une preuve d'optimum global pour 30 shifts. Les petits cas exhaustifs de Claude sont utiles, mais limités à ces cas.
4. `covers()` parcourt les agents et fait des `agents.find` dans la boucle ; pré-indexer agents et shifts une fois, maintenir les compteurs d'ouverture/fermeture pendant les échanges. Éviter un nouveau solveur complexe avant ces corrections.
5. Même convention de présence fractionnaire dans Monthly, Intraday et banc : cela supprime du code contradictoire au lieu d'ajouter des coefficients compensatoires.
6. Les tokens CSS nouvellement introduits sont référencés ; pas de purge massive suggérée sans inventaire des écrans et exports. Les couleurs de Calendar écrites en JS et la couleur de secours du logo restent en dur : la note « toutes les couleurs » doit être limitée à ce qui a réellement été converti. Aucune rupture visible attribuée à ces constantes dans cette passe.
7. Ne pas ajouter maintenant l'écran insights/audit : Roman l'a gardé pour une discussion ultérieure. Les diagnostics réutilisables prépareraient ce travail sans élargir cette livraison.
