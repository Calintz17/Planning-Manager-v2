## 2. Incidents de code

### P1 — Le passé change encore avec « Rest days per month »

Candidate lignes **5724–5734**, particulièrement :

```js
var share = regulations.weekly_hours > 0
  ? Math.min(1, contractHours(a) / regulations.weekly_hours) : 1;
var cap = Math.max(0, Math.round((nDays - restPerMonth) * share) - away);
```

`contractHours(a)` sans date retourne la valeur actuelle. Le reste du moteur peut lire correctement les anciennes semaines : cette limite mensuelle les rabote malgré tout.

**Reproduction indépendante :** horloge au 1er décembre, génération de novembre ; agent synthétique a12 sans absence, référence boutique 37,5 h, dix repos mensuels. Comparer deux historiques identiques sur tout novembre ; seule la valeur à partir du 1er décembre change.

| | Décembre reste à 37,5 h | Décembre passe à 21 h |
|---|---:|---:|
| `contractHours(a,'2026-11-01')` | 37,5 | 37,5 |
| Journées générées en novembre | **20** | **11** |
| Heures comptées novembre | **150** | **82,5** |
| Référence novembre | 160,714 h | 160,714 h |

**Cela porte sur la régénération du mois, pas sur une écriture automatique dans un ancien snapshot.** La promesse « le passé ne change jamais » n'est néanmoins pas tenue.

**Correction demandée :** passer une date ou une période explicite à toutes les lectures de contrat participant à un calcul. Pour conserver la formule de proportion mensuelle existante, une correction locale possible est une part moyenne datée :

```js
const share = monthDays.reduce((sum, d) => sum +
  Math.min(1, contractHours(a, d.ds) / regulations.weekly_hours), 0)
  / monthDays.length;
```

Conserver la garde actuelle lorsque le défaut boutique est nul. Cette correction préserve le modèle de prorata actuel ; elle ne tranche pas une nouvelle politique de repos pour les contrats mixtes. Vérifier aussi les autres appels sans date : contrôle d'horaire fixe L5850, gardes L6590/L7619, libellé historique L7388. La fiche courante peut légitimement lire le contrat courant ; un calcul ou libellé d'un mois passé doit indiquer sa période.

**Test requis :** si deux historiques sont identiques avant décembre, aucune modification postérieure ne change novembre, y compris avec repos mensuels actifs. Ajouter un cas de changement en milieu de mois et un cas fixe/flexible.

### P1 — Deux OFF / exploitation des shifts : correction toujours absente

`medianPaid` / `weekCap`, **L5594–5603**, conserve `floor(heures / durée médiane)` comme plafond de jours. L'ajout d'un shift plus court n'ouvre donc pas la possibilité d'une cinquième journée si la médiane reste inchangée.

Nouveau passage sur la 9.4.0.3 : **290 personnes-semaines complètes** octobre–décembre, hors semaines tronquées.

- Temps plein ordinaire sans absence/formation/fermeture : managers/vendeurs **200/200 avec deux OFF** ; stock **38/38 avec trois OFF**.
- Part-time fixes : trois ou cinq OFF, conformes aux jours fixes ; ne pas imposer deux OFF à ces personnes.
- Absence toute la semaine : zéro code OFF peut correspondre à sept cellules A, sans aucun travail. Ne pas confondre le code affiché et des jours travaillés.

Trois scénarios stock rejoués, semaine du 2 novembre :

1. Catalogue 8 h payées, contrat 37,5 : quatre jours/32 h/trois OFF pour les personnes sans absence. Cinq journées sont impossibles sous ce plafond.
2. Tous les shifts stock ramenés à 7,5 h dans le test : cinq jours/37,5 h/deux OFF.
3. Catalogue initial + S7 de 7,5 h : toujours quatre jours/32 h/trois OFF. Le défaut de sélection reste.

Le témoin hebdomadaire à cinq S7 validé dans l'audit précédent montre pourquoi une médiane n'est pas une preuve d'impossibilité. Chercher une combinaison de shifts admissibles sous budget, puis valider couverture/repos/actions manuelles. Ne pas corriger en ajoutant aveuglément un jour après génération ni en relevant les heures.

## 4. Arbitrage distinct : date effective en milieu de semaine

La fiche écrit une entrée **aujourd'hui** (L7870–7878), mais les plafonds hebdomadaires et le plafond de crédits lisent le contrat **du lundi** (L3459, L7606). La référence du mois et le crédit journalier utilisent la date du jour.

Ainsi, une réduction le mercredi est visible dans certaines valeurs dès mercredi mais le plafond de la semaine reste l'ancien jusqu'au dimanche. Ce comportement est expliqué par Claude ; **je ne le considère pas comme une règle approuvée par la seule décision « protéger le passé »**.

Proposition simple à confirmer : les changements s'appliquent au prochain lundi pour tous les calculs, avec indication de cette date, si c'est acceptable opérationnellement. Si une prise d'effet réelle en milieu de semaine est nécessaire, définir explicitement le budget de cette semaine et conserver les heures déjà faites. Ne pas introduire silencieusement une moyenne réglementaire supposée universelle. Le cas nominal testé par Claude change un lundi et ne teste pas cet arbitrage.

Autre point métier inchangé : les vraies durées stock doivent être compatibles avec le contrat ; cinq shifts de 8 h, deux OFF et plafond 37,5 h sont incompatibles.

## 6. Architecture : progrès et limite de la nouvelle couche

**Progrès :** `result.hours` partagé, `validCell`, comparaison des violations par clé et amplitude, CHECK SQL qualifié par table. Ces changements réduisent réellement les divergences.

**Faiblesse centrale : la date est facultative.** `contractHours(a, ds)` offre une API datée mais conserve un fallback silencieux courant dès qu'un appel oublie ds. La régression du plafond mensuel en est la conséquence directe.

Proposition pour Claude :

- `contractHoursAt(a, date)` exige une date pour le moteur ; `currentContractHours(a)` est réservé à la fiche courante.
- Un contexte daté commun fournit contrats, horaires fixes, calendrier et cellules. `accountDay`, objectifs et validation le lisent.
- Une source commune pour les heures ne signifie pas encore un historique complet : horaires fixes, catalogue de shifts et paramètres de déjeuner restent actuels. Leur modification peut revaloriser un ancien planning. Ne pas présenter la seule colonne d'heures comme une garantie d'immutabilité de tous les calculs passés.
- Pour les périodes validées, conserver les durées nécessaires dans le snapshot ou versionner les paramètres utilisés. Faire ce choix séparément, sans empiler des exceptions sur chaque export.
- Sauvegarde agent/préférences toujours en deux requêtes : préparer une écriture atomique. Statut de validation toujours non conservé dans le snapshot ; `finalCheck` encore couplé aux globals.
- Garder le refactoring limité : corriger les lectures non datées et la sélection des shifts, puis fermer les tests. Pas besoin d'une réécriture complète ni de suppression CSS spéculative.
