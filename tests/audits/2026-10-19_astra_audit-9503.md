## 2. Incidents du code public — pas de nouvel arbitrage

### B. P2 production — Le retry de démarrage ne couvre pas les promesses rejetées
`retail.html:1794–1808`, startWorkspace :
```js
workspaceStarted = true;
showLoader();
const { data, error } = await sb.from('retail_regions').select('*').order('name');
hideLoader();
if (error) { workspaceStarted = false; refuseAccount(...); return; }
```
La correction fonctionne quand le client renvoie {error}, comme le probe de Claude le teste. Elle ne fonctionne pas si la promesse rejette.

**Reproduit :** order() → Promise.reject(Error('network reject')) ; l'exception remonte et workspaceStarted reste true. L'appel suivant sort immédiatement. hideLoader n'est pas appelé sur ce chemin. Même risque sur les await de loadManagerStores/loadMe.

**Correction simple :** une frontière try/catch autour du démarrage, finally pour le loader, remise à zéro de l'état sur tout échec. Await le traitement refuseAccount. Garder un seul responsable de la déconnexion/retry.
```js
if (workspaceStarted) return;
workspaceStarted = true;
showLoader();
try {
  await initialiseWorkspace(); // pas de marqueur de succès prématuré
} catch (error) {
  workspaceStarted = false;
  await refuseAccount(t('Could not load your account. Try again.'));
} finally {
  hideLoader();
}
```
Schéma indicatif : conserver le traitement des {error} et éviter la double traduction. Ajouter un test rejeté, pas seulement failOnce={error}. Sign in et Save password libèrent bien leurs boutons avec finally dans cette version.

### C. P2 UI — Calendar déborde sur les téléphones de 320px

Contrôler les mois traduits longs et le conteneur parent avant intégration. Conserver les boutons tactiles 44px.

### D. P1 avant le futur workflow, pas panne actuelle — Le contexte ne survit pas au JSON
`copyMonthlyValue` 7764, `buildMonthlyContext` 7772, `validatePlan` 7779.
Le contexte conserve monthlyRef comme objet Date. Le test livré vérifie une copie **en mémoire**. Un stockage Supabase JSON transforme cette Date en chaîne.

**Reproduit :**
```js
const ctx = buildMonthlyContext();
const plan = pickMonthlyPlan(ctx);
validatePlan(plan.cells, JSON.parse(JSON.stringify(ctx)));
// TypeError: date.getFullYear is not a function
```

**À faire avant « envoi au directeur » :** définir un contexte JSON versionné, avec mois YYYY-MM et date de référence YYYY-MM-DD. Hydrater explicitement les anciennes entrées Date au point d'entrée tant que le moteur les exige. Même contrat pour calcul et recontrôle. Tester le vrai aller-retour JSON, puis le changement du live après ce round-trip.

Autre résultat : Object.freeze(Date) ne bloque pas setFullYear. Le monthlyRef du contexte peut être muté malgré freezeMonthlyValue. Une chaîne primitive pour le mois résout les deux problèmes. L'empreinte ne doit pas rester celle d'un contenu ensuite modifié.

Ne pas prétendre que ce constat casse aujourd'hui la lecture du planning courant : le futur stockage du contexte n'est pas encore en production.

## 4. Sobriété et prochaine architecture
La production mesure **9 804 lignes / 548 581 octets**. Le gros calcul reste environ 1 900 lignes. **Il n'existe pas de preuve de « 1 200 lignes inutiles »** ; ne pas viser un nombre arbitraire de lignes supprimées.

Ce qui a réellement progressé :

- fonctions leaveRes, fixedRes, outsideRes partagées ;
- liste manager plate, périmètre déduit de la boutique ;
- une fonction validatePlan réutilisable hors rendu, encore fondée sur une installation temporaire des variables globales.

Ordre concret pour Claude :
1. Corriger le démarrage sur exception et la navigation Calendar à 320px.
2. Stabiliser le format sérialisable de contexte (D).
3. Extraire un état du mois explicite : assignedMap, weekPaid, shiftPlanByDay, demi-journées. Passer cet état aux fonctions sans ajouter une seconde copie globale.
4. Extraire les compteurs hebdomadaires, puis les phases de placement/réparation une à une. Cellules identiques à chaque extraction.
5. Dédupliquer les **faits** communs : durée payée, classification du jour, lecture du contrat daté et des jours voisins.
6. **Ne pas supprimer l'indépendance du contrôle final** pour gagner des lignes : le générateur choisit, le validateur vérifie. Réutiliser les primitives de données ; garder des tests capables de détecter un mauvais planning que le générateur aurait produit.
7. Ajouter des tests par mutation : partir d'un planning valide et introduire volontairement absence de fermeture, dépassement, corner incohérent, code inconnu, cellule manquante. Vérifier le diagnostic précis. Une simple égalité à l'ancienne version peut conserver une erreur ancienne.

Une extraction ne doit pas faire exploser les wrappers/globals. Objectif : une entrée de contexte, un état de travail, un résultat, un rendu. Pas de framework, pas de nouveau solveur requis pour ce découpage.

Conserver main/test et les chemins stables décidés. Pour comparer l'historique : extraire le fichier d'un commit en temporaire avec son SHA, puis appeler regression.cjs ancien nouveau. Pas de nouvelle branche par audit. Écrire les notes sur test sans remplacer un build de Claude en cours.
