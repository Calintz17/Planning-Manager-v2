## Incidents de code prioritaires

### P1 — buildHabits fabrique les présences manquantes
retail.html lignes 2109–2140 :
for (...) days[toDateStr(new Date(y, mo, dn))] = '';
var state = v === 'OFF' ? 'off' : 'work';

Reproduction isolée : un agent, learning_reference_months=['2026-09'], aucun override, aucune présence importée, aucun congé/jour fermé. buildHabits('2026-11-01') retourne 30 observations et workMonday=3,8918, soit une probabilité plafonnée à 98 % de travailler. Attendu : zéro observation connue.

Cela touche les nouveaux arrivants, contrats ayant changé et imports partiels. Deux salariés aujourd'hui présents mais absents d'un ancien classeur ne doivent pas recevoir tout ce mois en travail fictif.
Correction simple : manifeste par référence avec agents/périodes/jours explicitement couverts et états work/off/unknown ; unknown n'alimente pas le modèle. Si l'import ne contient que OFF/absences, le complément work n'est autorisé que pour une couverture complète et attestée. Les références humaines restent admissibles sans jugement sur leur style ; le contrôle demandé est la complétude technique.

### P1 — le compteur global fuit le futur et la fenêtre
retail.html lignes 5999–6002 :
Object.keys(planningOverrides[id] || {}).forEach(function(ds) {
 var c = planningOverrides[id][ds];
 if (c && c !== 'OFF') shiftHabit[c] = (shiftHabit[c] || 0) + 1;
});

Aucun filtre six mois/cutoff, contrairement à buildHabits.
Reproduction instrumentée en lecture locale : génération novembre 2026, seule entrée ghost/2027-01-04=C ; le compteur global est {C:1}. Le modèle principal retourne zéro jour, mais un autre bonus utilise tout de même ce C.
Correction : supprimer ce second compteur ou le dériver exactement de la sélection de références de buildHabits. Une seule sélection avant le mois cible, un seul dédoublonnage, une seule pondération. L'ID ghost souligne également l'absence de filtre du roster dans ce compteur.

### P1 — le garde-fou ne contrôle pas les minima ni les autres limites
retail.html lignes 6782–6808 :
gaps += (o ? 0 : 1) + (c ? 0 : 1);

Il teste o>0/c>0, pas o>=min_opening/c>=min_closing. Il ne contrôle pas heures, repos, séries, quotas, ni deux personnes par corner ; il compare seulement un total de trous, laissant déplacer une violation vers un autre jour/corner.
Reproduction synthétique : deux agents, shift couvrant ouverture et fermeture, minimum magasin 3, horaires/quotas réglés pour autoriser les journées. habitsGate.gaps=0 alors que les 30 jours sont sous le minimum (2/3).
Correction : validateur unique sur le planning final et frontières. Les préférences ne peuvent créer aucune nouvelle infraction. Si base et candidat sont invalides, garder l'état à résoudre par le manager ; ne pas certifier la viabilité en comparant des totaux de trous. Pas de nouveau panneau d'alertes permanent nécessaire.

### P1 — Reset efface une référence et change son sens
retail.html lignes 5118–5140. clearMonthOverrides() supprime les OFF, mais learning_reference_months conserve le mois.
Reproduction avec stub, sans écriture Supabase : Septembre listé comme référence, OFF du 7 septembre ; après reset, override vide et mois toujours listé. Avec le complément work de buildHabits, le repos devient présence.
Correction : séparer références importées et overrides d'exploitation, ou protéger les références contre ce reset. Un reset de modifications de planning ne doit pas transformer la donnée source. La protection est une exigence de fidélité des données, pas un désaccord avec les habitudes du manager.

### P1 migration — journal lisible et alimentable sans périmètre
SQL lignes 16–17 :
create policy "edits read" ... using (true);
create policy "edits insert" ... with check (true);

Le SQL n'impose aucune restriction de rôle/boutique à ces politiques. Pour les rôles disposant des privilèges SQL correspondants, toute ligne est lisible et toute ligne est insérable. Avec la clé client distribuée par le site, ne pas confondre RLS activée avec isolation.
Correction : politiques rattachées au modèle d'accès réel de l'application et validation de store/agent/actor. À défaut de modèle d'authentification approprié, ne pas exposer le journal à tous les clients ; garder la collecte côté service autorisé.
Ce SQL optionnel n'a pas été exécuté. L'accès effectif de chaque rôle n'a pas été testé sur une table déployée.

### P2 — old_value n'est pas le shift remplacé
retail.html ligne 5072 :
var oldV = (planningOverrides[tAgent] || {})[tDs] || null;

Reproduction stub : cellule générée O, manager choisit C. Le journal écrit old_value=null,new_value=C, au lieu de O→C.
Correction : capturer la cellule réellement affichée avant édition, avec baseline_revision ; distinguer suppression d'override et choix d'un nouveau shift. Le modèle courant ne dépend pas du journal, mais la trace doit être fidèle pour la future attribution des décisions humaines.

### P2 migration — SQL non rejouable intégralement
CREATE TABLE/INDEX sont idempotents, CREATE POLICY ne l'est pas : les deux politiques déjà existantes provoqueraient une erreur à la seconde exécution.
Correction : migration versionnée ou contrôle d'existence par pg_policies avant CREATE POLICY. Ce constat vient de la lecture, pas d'une exécution SQL de production.

## Optimisation / simplicité
Points positifs : suppression de la requête des trois snapshots utilisés comme apprentissage ; CSS et structure UI inchangés.
À simplifier : double apprentissage shiftHabit + buildHabits ; seuils de tri et bonus répartis entre managers/stock/ventes ; fallback qui relance renderMonthlyPlanning jusqu'à trois fois.
Le render sans habitudes peut sauvegarder avant la sélection définitive, puis le render final sauvegarder encore : séparer calcul pur, validation, choix, puis un seul rendu et une seule sauvegarde. Lire la même capture d'entrée pour les deux candidats.
Les comparateurs à seuil likeDiff peuvent ne pas être transitifs lorsqu'ils basculent entre habitude et jours restants ; préférer un score continu explicite et un départage stable, à tester sans modifier les filtres d'admissibilité.
Pas de preuve justifiant une purge large de CSS ancien dans cette version ; ne pas mélanger nettoyage visuel et correction du moteur.
