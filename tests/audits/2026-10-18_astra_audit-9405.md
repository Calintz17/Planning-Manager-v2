## Incidents de code à corriger

### P1 — L'absence Monthly n'a pas le même effet que l'absence Calendar

Reproduction : vendeur synthétique a12, contrat 37,5h, semaine complète 2–8 novembre, une absence lundi.

| Saisie | Résultat lundi–dimanche | Travail | OFF |
|---|---|---:|---:|
| `planningOverrides.a12['2026-11-02']='A'` | A O C C O M OFF | 5 jours / 37,5h | **1** |
| Même absence dans `agentLeaves` | A OFF OFF C C O C | 4 jours / 30h | **2** |

Le bouton A existe réellement dans l'éditeur Monthly (lignes 5107–5113). Ce n'est pas un état artificiel inaccessible.

**Cause :** `isBlocked` (5663–5668) bloque maintenant la case A, mais le calcul `absW` (5711–5737) ne compte que `agentOnLeave` et `availability`. Il continue à demander cinq shifts ailleurs. Le salarié doit donc récupérer une absence selon le point d'entrée utilisé. Le validateur ne détecte pas cette différence : cinq shifts ne dépassent pas son plafond de travail.

**Attendu :** quatre shifts, une absence et deux OFF, identiques quelle que soit la saisie. Ajouter ce test au banc obligatoire. Corriger le quota, pas le nombre affiché dans la colonne OFF.

### P1 — Un shift manuel qui remplace une absence garde une déduction fantôme

Même personne / même semaine : une absence Calendar le 2 novembre, puis un O manuel sur ce jour.
Résultat : **O C OFF OFF OFF O M**, soit quatre shifts et trois OFF.

**Cause :** `shiftFor` (7028–7034) donne priorité au shift manuel, mais `absW` déduit encore la ligne Calendar. La préaffectation ajoutée à 5920–5928 compte correctement le O ; elle ne corrige pas la cible réduite à quatre.

La règle de priorité n'est pas à réinventer dans le quota : il doit lire la même décision que l'affichage. Si le produit veut au contraire interdire le remplacement d'une absence, l'éditeur doit l'indiquer explicitement ; le comportement actuel ne peut pas être à la fois O à l'écran et absence dans la cible.

**Attendu selon la priorité déjà codée :** cinq shifts / deux OFF. Le test joint échoue volontairement sur les deux P1.

### P2 — Normalisation OUT incomplète, cas de robustesse

Un override brut OUT donne `data|a12|2026-11-02` : `shiftFor` retourne `{code:'OUT'}` sans `special:'out'`, contrairement à Calendar. `validCell` (7665–7671) le rejette.

**Portée :** l'éditeur Monthly actuel propose A et OFF, pas OUT. Ce test est un contrôle d'import / de robustesse, pas la preuve d'un parcours utilisateur courant cassé. La note Claude mentionne néanmoins les formations parmi les valeurs manuelles traitées. Normaliser OUT au même endroit que A et OFF avant tout usage.

## Proposition ciblée pour Claude : une décision de journée, plusieurs compteurs

Ne pas ajouter une quatrième lecture indépendante des absences. Créer un petit résolveur commun utilisé avant les quotas, puis par l'affichage et le contrôle final :

```js
function effectiveMarker(a, ds) {
  const manual = (planningOverrides[a.id] || {})[ds];
  if (manual) return markerFromCode(manual); // shift, OFF, A, OUT
  const leave = agentOnLeave(a.id, ds);
  if (leave) return markerFromLeave(leave);
  if ((availability[a.id] || {})[ds] === 'absent')
    return { kind: 'absence', reducesQuota: true };
  return null; // moteur libre de choisir
}
```

C'est un schéma d'interface, pas un patch prêt à coller : les fonctions de conversion restent à écrire et les fermetures/contrats fixes doivent conserver leurs règles.

| État effectif | Disponible au floor | Réduit la cible de jours à attribuer | Compte dans les jours travaillés |
|---|---:|---:|---:|
| OFF | non | non | non |
| A | non | oui | non, crédit d'absence séparé |
| OUT | non | oui | oui |
| Shift manuel | oui, heures du shift | déjà affecté, ne pas le redéduire | oui |

Le quota doit distinguer **cible totale**, **jours crédités d'absence/formation** et **shifts déjà verrouillés**. La formation consomme aussi ses minutes et ses limites de jours. Ne pas assimiler une absence de cinq jours à cinq jours de repos, ni obliger un temps partiel à avoir exactement deux OFF.

## Contrôle final et architecture

- `computeMonthlyPlan` échange encore des globals via `useMonthlyInputs`. Une extraction progressive de fonctions lisant explicitement le contexte serait préférable à une réécriture complète.
- Ne pas supprimer arbitrairement du CSS « inutilisé » sur une seule capture : états responsive, print et menus sont conditionnels. Aucun lien mort ou CSS mort supplémentaire établi dans cette passe. Les commentaires de correctifs et les palettes Excel/CSS dupliquées méritent une consolidation ultérieure, pas un nettoyage risqué dans ce correctif.
