## 2. P1 NOUVEAU — Le cache retrouve le résultat mais son peintre refuse de le réafficher

### Reproduction

1. Mode figé (`manualMode = true`), snapshot chargé et vide, mois de novembre.
2. Premier affichage : calcul, peinture et sauvegarde du planning.
3. Changement de langue ou de corner sans changement métier.
4. `pickMonthlyPlan()` retrouve exactement le même résultat et sa clé correspond à l'empreinte courante.
5. `run.paint()` retourne pourtant **false**.

Résultat VM :

```json
{"firstPaint":true,"cacheHit":true,"keyMatches":true,"secondPaint":false,"filteredPaint":false,"foreignPaint":false}
```

Confirmation Firefox : **première peinture true, seconde false ; 35 lignes avant le filtre et 35 après**, aucun message d'erreur. Le filtre peut paraître sélectionné alors que son tableau n'a pas été redessiné. Ce scénario ne nécessite ni erreur réseau ni concurrence.

### Cause précise

`computeMonthlyPlanOn()`, **8133–8143**, conserve le contexte de départ dans la fermeture `paint()`. Après `keepShownPlan()`, il actualise uniquement la clé du cache :

```js
lastMonthlyRun = {
  key: monthlyFingerprint(monthlyInputs(), toDateStr(new Date())),
  run: this
};
```

Mais `paintMonthlyPlan()`, **8164**, compare encore l'ancienne empreinte :

```js
if (ctx.fingerprint !== monthlyFingerprint(monthlyInputs(), toDateStr(new Date())))
  return false;
```

Le snapshot a changé après le premier affichage : le cache et le peintre n'utilisent plus la même identité d'entrée acceptée.

### Correction ciblée proposée

Conserver **le contexte original immuable**, notamment pour la provenance et le contrôle. Ajouter à ce résultat une empreinte de réaffichage acceptée, initialisée à `ctx.fingerprint`, puis actualisée uniquement dans le cas déjà prévu de sauvegarde du même planning en mode figé. Le peintre vérifie cette empreinte. Ne pas enlever le contrôle d'obsolescence, ni fabriquer un faux contexte d'origine avec les données nouvelles.

Un patch de proposition accompagne cet audit : `tests/audits/2026-10-19_astra_retail-100006-cache.patch`. Il a été appliqué **à une copie locale seulement**. Le nouveau test passe : première peinture, réaffichage et filtre true ; autre boutique false. Dans Firefox, le filtre passe alors de 35 à 29 lignes, avec zéro erreur JavaScript. Ce succès ciblé ne vaut pas validation complète du patch : Claude doit rejouer la batterie avant de le livrer.

Test partagé : `tests/retail/bm/checks/cache-render-astra.cjs [build]`.

### Trou dans le test existant

`checks/cache.cjs` compte les calculs et sauvegardes. Il ne vérifie pas la réussite du peintre ou la modification effective du tableau filtré. Ajouter des assertions sur le DOM, les lignes attendues, les libellés traduits et la réussite du rendu. Tester également une sauvegarde refusée, une modification métier, une autre boutique et le passage de date. Aucune réparation ne doit permettre d'appliquer un résultat obsolète.

## 4. Architecture : gain réel, frontière encore incomplète

### Ce qui est bien réalisé

- `effectiveCornerId()` remplace les deux copies de recherche de corner.
- `contractHoursFor()` explicite les entrées de la règle de contrat ; l'adaptateur préserve les anciens appels.
- `paintMonthlyPlan()` ne contient plus l'écriture Supabase ; `keepShownPlan()` la porte. L'enchaînement reste assuré par `run.paint()` : c'est une séparation de responsabilités utile, pas encore un contrôleur entièrement indépendant.
- `renderIntraday()` prépare le mois manquant ; `paintIntraday()` n'appelle plus le rendu Monthly à l'intérieur de son calcul de pauses.
- Les blocs automatiques sont produits dans `buildIntradayModel()` et consommés par écran/export. Les déplacements manuels, y compris hors fenêtre automatique, restent prioritaires.
- Langue et corner d'affichage sont exclus de l'empreinte métier ; version du moteur et date sont incluses ; Recalculate force un calcul. Le jour utilisé reste celui du navigateur : une notion de date locale boutique n'a pas été ajoutée par ces lots.

### Ce qui reste à compléter, sans nouvelle réécriture

`buildIntradayModel()`, **5010–5530**, lit encore les variables globales. Cela est cohérent avec le report convenu du contexte complètement indépendant, et n'est pas une régression à lui seul.

Mais le modèle n'est pas encore entièrement autonome pour son export :

```js
// buildIntradayModel : références encore vivantes
return { a: a, sh: shiftInfo[a.id], blocks: blocks,
         added: addedMissions[a.id] || [], reinf: reinforceMissions[a.id] || [] };

// toIntradayExport : relecture de définitions et de la boutique courantes
var md = missionDef(m.type);
var dur = missionDurH(m);
// ... storeId: currentStoreId
```

Sources : **5525**, **5532–5559**, et nouvelle lecture des mêmes définitions dans le peintre **5633–5643**. Une extraction réussie ne signifie donc pas encore « une seule résolution de toutes les missions ».

**Amélioration sobre :** résoudre dès la construction du modèle les missions ajoutées : identifiant, type, début, durée numérique, clé de libellé, classe et couleur. Ajouter `storeId` au modèle. Copier les champs nécessaires de la personne au lieu de conserver l'objet vivant entier. L'écran traduit les clés et dessine ; l'export convertit les unités. Aucun des deux ne redétermine la durée depuis `regulations.breaks`.

Exemple de forme cible, à intégrer progressivement :

```js
function resolvedAddedMission(m) {
  var def = missionDef(m.type);
  return {
    id: m.id, type: m.type,
    startMin: m.start * 60,
    durationMin: m.dur || def.dur,
    labelKey: def.label, shortKey: def.short,
    cssClass: def.cls, color: def.color || null
  };
}
```

Ce résolveur est appelé une fois lors de la construction, avec le même comportement de durée que le code actuel. Les modifications manuelles restent prioritaires, sans arrondi ajouté ni clamp aux fenêtres automatiques. Test d'acceptation : construire un modèle, changer ensuite les réglages et la boutique courants, vérifier que son export conserve sa boutique et ses durées d'origine. Ne pas introduire maintenant de cache Intraday supplémentaire.
