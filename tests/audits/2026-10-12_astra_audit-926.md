## Incidents et limites de code — propositions pour Claude

### C1 — P2 : Weekly rest ne contrôle pas réellement toutes les valeurs proposées
Champ Settings autorise0..72h. restAllows ne regarde que le jour précédent et l’avant-veille ; si le dernier shift est plus loin, il rend true. restFits a la même portée. Il n’y a pas de contrôle final dur de tous les repos requis.
Vers5361 :
`var p2 = prevDayOf(prevDs);`
`return !ph2 || (2880 + th.start - ph2.end) >= weekRestMin;`
check_rules.js vers33 ne compte que des shifts espacés d’exactement deux dates, donc reproduit la même limitation.

Contre-épreuve indépendante : avec weekly_rest_hours65 sur le même fixture,139 gaps courts subsistent chez les agents hors PART_TIME, sans OUT dans le gap. Exemples agrégés :39,5h après un jour OFF,63,5h après deux OFF. Le réglage65 peut rendre les contrats/couvertures impossibles ; ce n’est pas un motif pour continuer à générer comme si le contrôle passait.
Ce n’est pas une violation reproduite à35h dans le scénario courant ; c’est une limite du nouveau champ dans sa plage autorisée.

Proposition simple :
- distinguer le profil de repos requis par période d’un minimum artificiel autour de chaque OFF ;
- chercher dernier/prochain travail connu sur toute la fenêtre, pas seulementJ-2/J+2 ;
- valider le résultat final avec un contrôleur indépendant ;
- si le contrat/configuration rend ce repos impossible, diagnostic explicite, pas retour true ou claim de conformité ;
- les repos de plusieurs jours ne doivent pas échapper au seuil sélectionné.
Éviter de programmer une nouvelle passe corrective différente pour chaque durée.

### C2 — P2 : calcul des repos en1440/2880 ignore le changement d’heure
Les formules utilisent la différence de jours civils multipliée par1440, pas des instants réels dans la timezone boutique.
Contre-exemple arithmétique, Europe/Paris : samedi27/03/2027 à21h → lundi29/03 à8h =34h réelles au passage à l’heure d’été ; formule48+8-21 renvoie35.
C’est une preuve du défaut de calcul, pas un replay global du planning2027.
Proposition : dates locales + timezone IANA → instants, puis différence de minutes réelles. Ne pas utiliser la timezone du navigateur pour toutes les boutiques. Ajouter un test printemps et automne.

### C3 — P2 : contrôle fixe incomplet sur catalogue sans horaires imposés
Dans fixedScheduleIssue vers2095 :
`if (fx.end > fx.start && regulations.max_daily_hours > 0 && paid > ...)`
Le test quotidien ne s’applique qu’aux horaires explicitement saisis.
Contre-épreuve : catalogue unique08–18 (9h payées), fixed4jours sans horaires, plafond journalier8,5h et hebdo40h → fixedScheduleIssue renvoie vide. Or aucune journée du catalogue ne tient le plafond.
Proposition : valider aussi le plus petit shift admissible par jour quand pas d’horaires. Si aucun shift ne tient, refuser la configuration, en expliquant le problème. Les entrées existantes peuvent être incohérentes même si le créateur de shifts empêche normalement cette situation.

### C4 — état historique incompatible conservé, pas hard block final
Le scénario fixe déjà en base5×08–18 garde quatre semaines à45h sous contrat37h30 ; toast de diagnostic, pas correction automatique. Comme925, le check final exclut toujours les horaires fixes.
La nouvelle validation empêche une création incompatible, pas toutes les données anciennes ni tous les recalculs après changement des Labor rules.
Proposition : diagnostic préalable de tous les contrats fixes ; distinguer « planning contient un contrat à corriger » de « aucune violation ». Ne pas enlever des jours fixes automatiquement. L’autorisation de conserver l’historique n’est pas une preuve de conformité.

### C5 — OUT/contrats inconnus : « non vérifié » n’est pas « valide »
restAllows et weekRestOk rendent true lorsque OUT sans heures est rencontré. L’aide dit maintenant que ces heures sont inconnues : transparence améliorée.
Mais le banc affiche0 violations sans compter les contrôles indéterminés.
Proposition : résultat à trois états dans l’audit (valid/invalid/unknown), nombre de gaps non vérifiables ; pas de toast intrusif nouveau. Une journée OUT compte pour les jours ; elle n’est pas du repos. Ne pas déduire un horaire arbitraire.
